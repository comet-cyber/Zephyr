# Titan 开机 UDP 抓包分析

采集时间：2026-10-20 11:19:54–11:22:03（Asia/Shanghai）。

## 已验证事实

- 用户本轮串口输出：`UDP example started`、`socket created, fd=0`、`UDP send returned 16 bytes`、`socket closed`。
- 11:20:51.639，Windows 收到 Titan 的 ARP 请求并回复自己的 MAC；11:20:51.640，实体网卡收到 UDP 数据报。
- Ethernet：`74:90:50:01:02:03 → BC:FC:E7:EC:E9:3B`。
- IPv4/UDP：`192.168.50.2:38823 → 192.168.50.1:4242`。
- IPv4 总长度 44 字节、UDP 长度 24 字节、应用数据 16 字节：`b'Hello from Titan'`。
- 用 Python 标准库直接解析 pcapng、对网卡入站原始帧计算校验和：IPv4 头校验和 `0x956d` 正确；UDP 校验和 `0x8d27`（含 IPv4 伪头）正确。
- Windows PktMon 在 TCP/IPv4 L3/L4 组件 138 记录同一数据报的三条丢弃事件：`INET: receive inspection`、`INET: transport endpoint was not found`、`Inspection drop`。见 `packets.txt` 第 211、218、225 行附近。三条事件不能解释成发送了三包。
- 接收进程 PID 16780 当时仍绑定 `192.168.50.1:4242`，但没有收到该 Hello。复位后，本机向这个绑定发送 `pc-local-after-reset`，原接收进程确实收到，说明进程存活且本地 socket 接收正常。
- 此前板端执行 `net udp send 192.168.50.1 4242 probe` 时，原接收进程已真实收到来自 `192.168.50.2:49357` 的 `b'probe'`。
- Python 的 Public 入站 UDP Allow 规则已存在；未更改防火墙、网卡配置或路由。

## 判断边界

开机 Hello 已正确到达电脑网卡，问题已定位到 Windows 接收/过滤路径。不能继续归因为板端未发送、ARP 未完成、UDP 内容或校验和错误；也不能仅凭这些事件认定某个具体过滤器或软件是根因。

只读 WFP 快照见 `wfp-filters.xml`；`wfp-netevents.xml` 为空，不含这次丢弃对应的过滤器 ID，不能据快照证明命中了某条规则。FlClash TUN 已启用，同时有其他网络过滤驱动；尚未对任何软件归责或更改设置。

## 后续实验

原接收进程已由诊断方停止，随后使用原脚本的 `--host 0.0.0.0` 启动接收进程 PID 3492，验证指定 IP 绑定与接口复位的关系。该次抓包目录为 `../udp-bind-any-20261020-112843/`；窗口内没有捕获到 Titan 数据，接收器也没有收到 Hello，因此尚不能判断更换监听地址是否有效。已请求用户提供这一轮的完整启动输出，先不再次复位。


这验证了稳定运行时的单向 UDP 接收，不能证明通配绑定已经解决复位后的开机单次发送。此前指定 IP 绑定同样能接收手动 probe，故不能将绑定方式直接认定为根因。建议下一次教学增量将应用改为有间隔地发送多包、记录序号和结果，对比开机第一包与后续包，再决定是否需要继续查 Windows 过滤器；不要以关闭整个防火墙或直接加关闭前延时作为已证明的修复。

诊断结束已核对命令行并停止自建接收进程 PID 3492，释放 UDP 4242；临时 WFP 查询脚本已清理，采集/过滤器均已停止和清理。用户可在自己的终端运行原接收脚本，加 `--host 0.0.0.0` 复现已验证的监听方式。
